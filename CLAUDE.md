# Проект: ИИ-хакатон Туту MCP

Это **хакатон**, а не продуктовая разработка. Формат:

- Тема: проекты на базе **Model Context Protocol (MCP)** для задач путешественников на данных Туту.

**Единый рабочий документ — `SPECIFICATION.md`**: что делаем, доказательства проблемы,
сценарий демо, техническая реализация, регламент сдачи и критерии оценки.
Читать его перед любой работой по продукту.

**Времени на разработку ~10 часов.** Демо готовится на замороженном коде — «допилить ночью» нельзя.
Всё, что пишется, должно быть показуемо в этот срок.

## MCP-сервер Туту

- **Endpoint:** `https://mcp.tutu.ru/mcp`
- **Транспорт:** streamable HTTP (POST JSON-RPC; GET + `Accept: text/event-stream` для SSE;
GET + `Accept: text/html` отдаёт лендинг с инструкцией по подключению).
- **Авторизация не нужна** — проверено, `tools/call` отдаёт живые данные анонимно.
Поддерживается OAuth 2.1 и статический API-ключ в заголовке, но для работы это не требуется.
Токен в query-параметрах URL запрещён спекой MCP.
- **Rate limit:** есть, только на вызовы инструментов, при превышении — HTTP 429.
Не долбить сервер в цикле; кэшировать ответы поиска локально.
- Сервер: `tutu-mcp-server`, protocolVersion `2025-06-18`. Только чтение: поиск + сборка ссылки
на оплату. Никаких платежей, личных кабинетов и бронирований на стороне Туту.

### 16 инструментов

Поиск: `search_avia`, `search_rail`, `search_bus`, `search_etrain`, `search_hotels`,
`search_multitransport`.
Детали: `get_offer_details` (в т.ч. отзывы по отелю), `get_rail_seatmap` (схема вагона).
Чекаут: `create_checkout_link`. Прочее: `fetch_resource`.
Плейбуки: `get_avia_instructions`, `get_rail_instructions`, `get_bus_instructions`,
`get_etrain_instructions`, `get_hotels_instructions`, `get_multitransport_instructions`.

**Паттерн работы, заложенный авторами сервера:**

1. Перед первой работой с доменом один раз вызвать `get_<domain>_instructions` —
ам детальные поля, edge-cases и правила отображения (progressive disclosure).
2. Поиск → офферы с `price`, `legs[].segments[]`, `search_results_url`, опциональным готовым
checkout_url`и объектом`checkout_ref`. У avia/bus/etrain есть` variants[]`(тарифы,  каждого свой`offer_hash`), у rail — сводка` fares`+`seat_categories`.
3. Ссылка на оплату: готовый `checkout_url` либо `create_checkout_link` по `checkout_ref`.

У большинства инструментов **нет обязательных полей** и приняты легаси-алиасы
(`from_city`/`to_city` вместо `origin`/`destination`, `checkin_date`/`checkout_date` для отелей).
Есть параметр `view` (`compact` и др.) — использовать `compact`, ответы жирные (~30 КБ на запрос).

### Быстрая проверка сервера

```bash
curl -s -X POST https://mcp.tutu.ru/mcp \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{}}'
```

## На что смотрят судьи (в порядке важности)

1. **UX/UI** — весит больше, чем глубина функционала. Голый чат в терминале = провал по этому
ритерию. Нужна своя визуальная оболочка: виджет, веб-интерфейс, бот с нормальной вёрсткой.
2. **Глубина функционала** — сценарий должен быть доведён до конца, а не до заглушки.
3. **Соответствие теме**, **документация** (README пишем обязательно — дешёвые очки),
*инновационность**, **стабильность** (демо не должно падать).
4. **Архитектура и качество кода** — судьи реально читают репозиторий.
5. **Питч** — судья смотрит 30 презентаций подряд. Первые 30 секунд решают.

## Правила агента для этого проекта

Проектные правила приоритетнее глобальных. Здесь **явно отменяются** следующие глобальные:

- ❌ **Production-grade / no-MVP отменено.** Это хакатон: выбираем самое быстрое решение,
которое выглядит законченным. Никакого оверинжиниринга — без абстракций «на вырост»,
без слоёв, без DI, без плагинных архитектур, без микросервисов.
- ❌ Лимит 500 строк — ориентир, а не блокер. Не тратим время на рефакторинг ради лимита.
- ❌ Не пишем комментарий к каждому логическому блоку. Комментируем только неочевидное.

**Остаётся в силе:**

- ✅ Ответы пользователю — на русском.
- ✅ Никаких выдуманных дефолтов для обязательных данных и **никаких моков вместо реальных
вызовов MCP**. Демо должно работать на живых данных Туту — фейковый ответ судьи вскроют.
- ✅ Понятные ошибки для пользователя на русском, без технических деталей в UI.
- ✅ Docker для запуска, если проект того требует.
- ✅ Актуальные версии библиотек через `ctx7` — но не залипать на изучении доков.

**Правило про запросы к Туту (проверено на себе).** У сервера есть rate limit
вплоть до блокировки по IP на уровне TCP: 19 августа около полусотни проверок
подряд закрыли доступ ко всему домену `tutu.ru` на несколько часов. Поэтому:
не гонять curl напрямую, работать через `callTutu` (он читает кэш первым),
держать `MAX_HUBS_PER_SEARCH` маленьким, а перед демо прогревать кэш
командой `npm run warm` из папки `fixtures/`.

**Особое правило про стабильность демо:** на экране у судей ничего не должно падать.
Ошибки внешних вызовов ловим на границе UI, показываем аккуратное состояние ошибки и логируем —
это осознанное исключение из глобальной политики fail-fast, потому что стабильность оценивается.

**Как работать по ходу хакатона:**

- Сначала сквозной вертикальный срез (MCP → бэк → экран), потом наращивание.
- Каждый час — рабочее состояние, коммит. Ничего не ломать «на середине» перед дедлайном.
- Не начинать новую фичу, если до 21:00 МСК осталось меньше часа: это время на README,
чистку и подготовку демо.
- Не спрашивать разрешения на мелкие технические решения — выбирать самостоятельно
и говорить, что выбрано.

## Каркас уже собран (не пересоздавать)

Рабочий вертикальный срез MCP → агент → карточки готов и проверен на живых данных.
В день хакатона задание вкручивается в `lib/prompt.ts` и карточки, а не начинается с нуля.

- Приложение на **порту 3100** (`npm run dev`) — 3000 занят другим проектом на этой машине.
- Postgres в Docker на **порту 5433** (`npm run db:up`), postgres:18 монтирует том
в `/var/lib/postgresql`, а не в `/data` — иначе контейнер уходит в рестарт.
- `npm run smoke` — проверка MCP → кэш → выжимка без языковой модели. Гонять перед демо.
- `npm run mcp:probe [tool]` — сырой ответ любого инструмента Туту.
- `npm run route -- Москва Углич 2026-08-20` — сборка маршрута из командной строки.
- `npm run warm` — прогрев кэша из `fixtures/`, обязательно перед демо.
- `npm run cache` — что сейчас лежит в кэше.
- Замер на реальном поиске: полный ответ 26 305 символов, выжимка в модель 1 971,
экономия 93 %; повтор из кэша 2430 мс → 5 мс.

Версии на момент сборки: Next 16.3, AI SDK 7, `@ai-sdk/mcp` 2, Prisma 7 (обязателен
драйвер-адаптер `@prisma/adapter-pg` и `prisma.config.ts`), Tailwind 4, shadcn (radix-nova).

**Зачем база:** привычный для команды стек, плюс таблица `McpCache` реально закрывает
rate limit Туту — повтор поиска отдаётся из кэша за 5 мс вместо 2430 мс и не бьёт по их
серверу. `ChatSession` и `Message` хранят историю диалога вместе с вызовами инструментов,
поэтому сохранённый диалог открывается по ссылке `/c/<id>` вместе с карточками.

**Прототип нужен по публичной ссылке.** Организаторы проверяют ссылки сами и не засчитывают
материал, если что-то не открылось, поэтому одного `npm run dev` на ноутбуке для сдачи мало.
Разворачивание и выбор хостинга — открытый вопрос, см. `SPECIFICATION.md`.

## Архитектура

Код разложен по модулям — по смыслу, а не по типу файла. Зависимости
однонаправленные: `agent` → `routing` → `tutu`.

```
modules/tutu/client.ts        подключение к mcp.tutu.ru, кэш, обёртка инструментов
modules/tutu/types.ts         типы ответов Туту (нужны и клиенту)
modules/tutu/config.ts        адрес сервера, TTL кэша, лимиты для модели
modules/routing/builder.ts    ядро: узлы, оба плеча, стыковки, запасной план
modules/routing/hubs.ts       справочник «регион → центр»; регион даёт MCP
modules/routing/hub-suggest.ts подсказка городов моделью
modules/routing/config.ts     запас на пересадку, границы перебора
modules/agent/                агентный цикл (в работе)
app/                          роутинг Next: страница и API, тонкие
components/route/             интерфейс — здесь баллы за UX
lib/                          общее: конфиг интерфейса, палитра, форматтеры, Prisma
data/                         справочник городов для подсказок
fixtures/                     настоящие ответы Туту для разработки и прогрева
```

Слоёв `domain/`/`infra/`/`api/` внутри модулей нет осознанно: на трёх с половиной
тысячах строк они дали бы папки по одному файлу. Появятся, когда модуль
перерастёт тысячу строк.

**Чата в продукте нет** — решено осознанно: организаторы сказали, что разговорные
помощники утомляют, а у Туту свой ассистент уже есть. Языковая модель в расчётах
не участвует: регион даёт MCP, узлы — справочник, стыковки считает код.
Опционально модель может предлагать дополнительные города-пересадки, но всё,
что она предложит, проверяется живыми данными.

Плоско, без слоёв, DI и абстракций «на вырост». Вся интеграция с Туту — в одном файле,
всё поведение продукта — в одном промпте.

**Ключевой узел, закладывается сразу (переделывать потом дорого).** Инструменты MCP не отдаются
модели напрямую: в `lib/mcp.ts` они оборачиваются так, что **полный JSON уходит в UI и рисуется
карточкой, а в модель возвращается сжатая выжимка** (3–5 офферов: цена, время, ссылка).
Модель ведёт диалог и решает, что искать; таблицы и карточки рисует React, а не LLM.
Причина: ответы MCP ~30 КБ — прямая передача в модель означает медленно, дорого и пересказ
полей текстом вместо интерфейса.

Подключение MCP (AI SDK умеет это из коробки):

```ts
import { createMCPClient } from '@ai-sdk/mcp';
const client = await createMCPClient({
  transport: { type: 'http', url: 'https://mcp.tutu.ru/mcp' },
});
const tools = await client.tools();
```

**Страховка на трек «оптимизация инструментов»:** если задание окажется про улучшение самого MCP,
`lib/mcp.ts` разворачивается в собственный MCP-сервер-прокси на `/api/mcp` поверх Туту,
а фронт при этом не выбрасывается.
